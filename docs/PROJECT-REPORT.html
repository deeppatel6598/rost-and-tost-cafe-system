01 The problem and the product

What exists today, and what this replaces.

The canteen at Sakarchand Patel University is one hall shared by four independent businesses. They share the room, the tables and the students — and nothing else. Separate menus, separate staff, separate UPI accounts, separate cash.

StallSellsToken prefixMenu layout
Jay BhavaniGujarati snacks, thaliJBVertical category rail
La Pinos PizzaPizza, pasta, sidesLPOffer-led grid
Tea PostChai, maggi, bun maskaTPHero image and search
The Thick ShakeShakes, cold coffeeTSHero image and search

At lunch the hall fills, four queues form, and students spend most of their break standing in them. The system replaces the queue, not the counter: an order is placed from the table, and the student still walks up when their token is called. Nothing is delivered. That single decision removes an entire category of complexity — no runners, no addresses, no delivery states.

What it deliberately does not do

Scope discipline was a design goal, not an omission. The system has no delivery, no guest accounts or logins, no payment gateway, no single checkout spanning multiple stalls, and no loyalty, coupons or ratings. Each of those would have added a subsystem; none of them solves the queue.

Payment is the sharpest example. Integrating a gateway like Razorpay would mean settlement accounts, refunds and reconciliation for four separate businesses. Instead the student pays the stall's own UPI ID directly through a deep link, and a member of that stall's staff confirms receipt in their own UPI app before the order moves forward. The money never touches this system. That is a deliberate trade of automation for a much smaller trusted surface.

02 Language and technology stack

One language across the whole system, and the reasoning behind each dependency.

The project is written entirely in TypeScript — the browser code, the server code, the database queries and the seed scripts. There is no second language anywhere in the stack. That matters more than it sounds: a type defined once in src/lib/types.ts is the same type in the React component, in the API route and in the SQL result, so a mistake about the shape of an order is caught at compile time rather than at a counter during lunch.

Why no ORM

Prisma and Drizzle were both considered and rejected. The most important operations in this system — the sold-out race, the token sequence, order creation — are explicit SQL with row-level locking. An ORM would either hide that behind an abstraction or force an escape hatch back to raw SQL for exactly the queries that matter most. postgres.js gives parameterised queries (so SQL injection is structurally impossible) while leaving the SQL readable: 

// Values in ${...} are sent as bound parameters, never string-concatenated.
const items = await tx<MenuItem[]>`
  select * from menu_items where id in ${tx(unique)} order by id for update
`;

03 Architecture

Four layers, and a rule about which may talk to which.

LayerLives inResponsibility
Pages & componentssrc/app, src/componentsRendering and interaction. Never touches the database directly.
API routessrc/app/apiAuthentication, input validation, rate limiting, HTTP shape. Holds no business rules.
Storesrc/lib/storeAll business rules and all SQL. Transactions begin and end here.
DatabasePostgreSQLConstraints, foreign keys, row locks. The final arbiter of correctness.

The rule is that a rule lives in exactly one place. Tenancy is the clearest case: every stall-scoped store function takes a stallId and includes it in the WHERE clause, so even if an API route forgot to check, one stall still could not read or edit another's data. The route layer is a gate, not the wall.

Request lifecycle — placing an order

This is the most involved path in the system, so it is worth following end to end.

  1. Student scans the table QR code

    GET /t/<qrToken>. The token is an HMAC of the table number, verified server-side. A table number is never accepted from a URL or query parameter.

  2. A session cookie is issued

    A signed JWT holding { tableId, tableNumber, visitId }, httpOnly, four-hour lifetime. A visit row is opened for this sitting.

  3. Menu is served and a cart is built

    Cart state lives in React context on the phone. It carries item IDs and quantities — never prices.

  4. Checkout posts to the server

    POST /api/orders with a client-generated Idempotency-Key header, the line items, the payment method and a mandatory phone number.

  5. The route validates and throttles

    Session, phone format, idempotency key, rate limits. A request that replays an already-written key skips the limiter entirely, so a retry on bad wifi is never answered with "too many orders".

  6. One database transaction does everything else

    Lock the menu rows, re-check availability, recompute every price from the database, claim the visit, increment the stall's token sequence, write the order, sub-order, line items and idempotency key. All of it commits together or none of it does.

  7. The student gets a token and a payment route

    A token number like LP-042, a random public_token for the status page, and — for UPI — a deep link into their payment app.

  8. Stall staff confirm and advance

    Payment is confirmed by a human checking their own UPI app. Status moves PLACED → ACCEPTED → PREPARING → READY → COMPLETED, one tap per step, each guarded by a row lock.

A structural decision worth explaining

data/canteen.ts exists separately from data/seed.ts because seed.ts imports password hashing and the QR signing key. A client component that imported one string constant from it would drag scrypt and the signing secret into the browser bundle. That actually happened during development and produced a blank page whose server-rendered HTML was perfectly correct — a good illustration of why module boundaries in a full-stack framework are a security concern, not just tidiness.

Why line items store snapshots

If a stall raises the price of a pizza tomorrow, yesterday's receipt must not change. So each line stores the name, variant name and unit price as they were at the moment of ordering, alongside the item_id reference. Menu items are also soft-deleted (is_active = false) rather than removed, so order history never points at a missing row.

The order shape, and why it is split in two

An order is one checkout; a sub_order is the part of it belonging to one stall. Today a student checks out from one stall at a time, so there is exactly one sub-order per order — but the split is what would let a single basket span stalls later, and more immediately it is the right unit for the kitchen. Staff work sub-orders: each has its own token number, its own status machine and its own payment state, because the four stalls are separate businesses and one stall's pizza being ready says nothing about another's chai.

06 How data is managed

The part of the design that drove the database choice.

Why a relational database, and why transactions specifically

The system was first built against an in-memory store. That works until two students tap Order in the same millisecond. Three problems appear at once, and all three are transaction problems:

  • The sold-out race. Two students order the last plate. Both read "available", both succeed, one goes hungry. The fix is SELECT … FOR UPDATE on the menu row inside the writing transaction: the second transaction blocks, then reads the row the first one left behind and fails its check.
  • The token sequence. Two orders must never be given token LP-042. The counter is incremented with UPDATE stalls SET token_seq = token_seq + 1 … RETURNING token_seq — a single statement, so there is no window between reading and writing.
  • Partial writes. An order is four inserts across four tables. A crash between them would leave a sub-order with no line items, which is an order nobody can cook. Wrapping them in one transaction makes that state impossible.

None of this is achievable in application code alone once more than one server process exists — and on serverless hosting there are always several. The database has to be the arbiter, which is why PostgreSQL rather than a document store. 

// src/lib/store/orders.ts — everything from the availability check
// to the last insert happens inside one transaction.
return await sql.begin(async (tx) => {
  const catalogue = await loadCatalogue(itemIds, tx);   // locks the rows
  priced       = priceCart(stall, args.lines, catalogue); // prices from the DB
  const visit  = await claimVisit(args.visitId, phone, deviceHash, tx);
  const token  = await nextTokenNumber(stall.id, tx);
  // … insert orders, sub_orders, sub_order_items, idempotency_keys
});

Migrations

Schema changes are plain, numbered SQL files in db/migrations/, applied in order and written to be re-runnable (create table if not exists, add column if not exists). There are three so far. Keeping them as SQL rather than a framework's migration DSL means they can be read, reviewed and run by anyone who knows SQL, including a DBA who has never seen this codebase.

Connection management

This is the detail most likely to break a deployment. A direct PostgreSQL connection allows roughly sixty clients; a serverless platform starts a new function instance per concurrent request and will exhaust that during a single lunch rush. So the app connects through Supabase's transaction-mode pooler on port 6543, not the direct port 5432, and the client is configured to match: 

// src/lib/db/sql.ts
postgres(connectionString, {
  transform: postgres.camel,      // snake_case columns → camelCase objects
  max: isServerless ? 1 : 10,     // one connection per instance when serverless
  prepare: false,                 // required by the transaction-mode pooler
  idle_timeout: 20,
  connect_timeout: 10,
});

prepare: false is not optional: the transaction pooler multiplexes clients across backends, so prepared statements cached on one backend would not exist on the next.

Row-level security

RLS is enabled on all 17 tables with no policies granted. That is deliberate and it is the strictest setting, not the loosest: with RLS on and no policy, the anonymous and authenticated Supabase roles can read nothing at all. The application connects as the owner role, which bypasses RLS, and every access decision is made in the store layer where it can be tested. If Supabase's auto-generated REST API is ever exposed, it returns nothing.

Caching and state

There is no cache layer, and that is a considered choice for this scale. A canteen has four stalls and perhaps 300 orders a day; a Redis dependency would add an operational component to save milliseconds nobody will notice. Client state is minimal: the cart lives in React context, and localStorage holds only status links as a convenience — the server is authoritative for the order list, which is what makes closing a browser tab harmless.

08 Identity: the hardest problem

The part of this project with the most design in it, and the least code.

Early on, an order belonged to a table and to nothing else. A table is furniture: it does not order food, and it outlives the person sitting at it. That single modelling gap caused two failures at once:

  • A student closes the browser tab and loses their order list. The only handle on the order lived in that one browser's storage.
  • One student leaves and another sits down. Nothing distinguished them, so the new student saw the previous one's orders.

The answer is a visit — one student's sitting at one table — and the rule that the phone number is the identity, the table scopes who may claim it, and the cookie is only a fast path. The phone number is already mandatory at checkout, so this costs the student nothing extra.

SituationWhat happens
Closes the tab, reopensCookie still alive → same visit → orders are there.
Moves from table 7 to table 12Same phone, same browser → one list, both orders. The table does not own the order.
Finishes and leaves; someone else sits downThe new student orders with their own number → a different guest from that checkout onward.
Orders from a second phoneVerification by one-time code joins the sittings together.
Types someone else's numberSees only what that browser itself ordered. This is the attack that was closed.

The vulnerability, and the fix

Making the order list follow the phone number created a real hole. Someone at a table could type a classmate's number at checkout, be joined to their sitting, and read their token number — which is enough to walk up and collect their food when the counter calls it.

The fix is a one-time code, but deliberately not at checkout. Placing an order, paying and seeing the sitting you just paid for are never gated, because SMS in India routinely takes 30 seconds and sometimes never arrives — a telecom outage must not stop the canteen selling food. Instead the gate sits on the cross-visit history query: 

// A browser may see a sitting if either is true:
//   1. it opened that sitting itself   (visits.device_hash)
//   2. it has verified the number      (verified_phones)

Rule 1 is why most students never meet a code at all: the phone that placed the order keeps seeing it, so moving between tables needs no SMS. Rule 2 covers a genuinely different browser — a second phone, cleared storage, or someone typing a number that is not theirs. Verification lasts 90 days per device.

Code handling

  • Six digits from crypto.randomInt, never Math.random.
  • Only an HMAC-SHA256 of the code is stored, keyed by the server secret. A six-digit code has a million-value space, so an unkeyed hash would be exhaustible from a database dump in milliseconds; the server-side key is what makes a leaked row worthless.
  • Five wrong attempts burn the challenge. Five minutes to expiry. Single use, consumed by one conditional UPDATE so two submissions cannot both win.
  • Send limits live in Postgres, not process memory — an in-memory limit would multiply the SMS bill by the number of running instances.
  • Every failure returns one message and one shape, so the endpoint cannot be used to learn which numbers are real.
Known residual risk, stated deliberately

A student who hands their own unlocked phone to a friend is still that student as far as the app is concerned. No system fixes this and none should try. The prize is one meal inside a four-hour window, and defending further would cost every honest student time at lunch.

Secrets

A single AUTH_SECRET signs staff sessions, table sessions and the HMAC inside every printed QR code. In production the app refuses to start if it is missing, shorter than 32 characters, or equal to the development placeholder — rejected by name, because that value is published in the repository and is the one most likely to be copied across by mistake. The check runs at startup, so a misconfigured deploy fails at deploy time rather than one student at a time.

A consequence worth recording: rotating AUTH_SECRET invalidates every printed QR sticker. That is the intended lever if stickers are ever compromised, but it means the secret must be generated before the stickers are printed.

Passwords and headers

Staff passwords are hashed with scrypt. Response headers set HSTS, nosniff, X-Frame-Options: DENY, a Permissions-Policy and a Content-Security-Policy. Referrer-Policy is no-referrer and is load-bearing rather than decorative: this app deliberately puts secrets in URLs (/t/<qr token>, /status/<public token>) and a Referer header would hand them to whatever the browser talks to next.

A bug worth reporting honestly

The first version of that CSP set default-src 'self' without an explicit script-src, which blocks Next.js's inline hydration bootstrap through the default-src fallback. Every page rendered and was completely dead to the touch — and all 151 server-side checks passed against that build. Only a browser test caught it. It is the clearest example in this project of a class of failure that server-side testing cannot see at all.

10 Interface and design system

Designed for a phone held at arm's length in a bright, loud hall.

Every guest screen is built for a 390 px phone first. Tokens are set as CSS custom properties and consumed through Tailwind, so the four stalls are themed by a single data-stall attribute rather than four stylesheets — each stall gets its own accent while sharing every component.

Three menu layouts

The four stalls do not share a menu layout, because they do not sell the same kind of thing. Jay Bhavani has many categories and uses a vertical category rail; La Pinos leads with offers in a grid; Tea Post and The Thick Shake have short menus and use a hero image with search. The layout is a per-stall column in the database, not a hard-coded branch.

Accessibility, measured rather than assumed

  • Contrast was computed numerically, not eyeballed. An audit found every primary button failing WCAG AA at 2.62:1 — white text on the coral accent. It was fixed by splitting the accent into separate text and fill colours.
  • Every touch target is at least 44 × 44 px. An audit found four that were not (36–42 px) and all were raised.
  • Full light and dark themes; typography scales with the user's settings; motion respects prefers-reduced-motion; the viewport permits zoom up to 5×.

Errors are written for the moment they are read

Every dead end — a damaged QR code, a stale link, a render failure — says what to do next in the room rather than what went wrong in the software, and always offers the counter as the way out. No stack traces and no error codes: a student can do nothing with either, and a digest tells an attacker more than it tells them.

Method

The suites drive the real HTTP API against a real PostgreSQL database, then assert directly against the database with SQL. Concurrency is tested by firing genuinely simultaneous requests with Promise.all and checking invariants afterwards: no duplicate token at a stall, no gap in any sequence, every subtotal equal to the sum of its lines, no orphaned rows, and the stall counter matching the number of orders written.

Two principles the project stuck to are worth stating, because both caught real bugs: measure rather than eyeball — contrast ratios and touch targets were computed, not judged — and always confirm in a browser, since hydration and CSP failures are invisible to server-side tests.

Bugs found by testing that had not been reported

Around twenty, several security- or accessibility-critical. Examples: a public order endpoint returning the guest's phone number; a rate limit keyed to the table so everyone seated there shared one budget; a network retry of an already-placed order being answered with "too many orders"; the admin login page printing working credentials for all five seeded accounts; nested <button> elements causing a hydration error on every menu load.

Honest limitations

  • The rate limiter is per-process, so on multi-instance hosting the effective limit multiplies by instance count. A shared counter is the fix when it matters. OTP send limits are already in the database for exactly this reason, because those cost money.
  • Payment confirmation is manual by design. It is a human checking their own UPI app — deliberate, but it does mean a busy stall can fall behind on confirmations.
  • No admin "live tables" view showing who is seated where.
  • Single region. Fine for one campus; would need thought for more.

13 Running it

# 1. Install
npm install

# 2. Configure — copy .env.example to .env.local and fill in
AUTH_SECRET=$(openssl rand -hex 32)
DATABASE_URL=postgresql://...pooler.supabase.com:6543/postgres
CANTEEN_TIMEZONE=Asia/Kolkata
OTP_PROVIDER=console

# 3. Create the schema and seed it
psql $DATABASE_URL -f db/migrations/001_init.sql

npm run dev            # development
npm run build && npm start
